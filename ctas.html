Cowboy Transient Alert System

CTAS

A rights-aware research system for reconciling supernova and multimessenger alerts with public follow-up evidence — so that a researcher can see, in one place, what was reported, what is known about the field it landed in, and what is worth doing next.

Active development Runs locally · not publicly deployed Version 1.2.0

The problem

Transients do not wait

Events change quickly

A supernova, a gamma-ray burst or a gravitational-wave event evolves on a timescale of hours to days. Whatever you are going to learn from the early behaviour, you have to decide to look for almost immediately.

Alerts arrive from everywhere

Discovery reports, circulars, broker streams and archival services each publish in their own format, with their own identifiers, on their own schedule — and with very different rules about what may be redistributed.

Context lives somewhere else

Deciding whether a candidate matters usually means asking what galaxy it sits in, what has been seen at that position before, and whether anyone has already reported a classification.

The record fragments

Triage decisions, follow-up plans and the reasoning behind them tend to scatter across notebooks, spreadsheets and email — which is exactly the material you need again when you write it up.

CTAS does not attempt to solve all of this. It addresses one slice: keeping rights-cleared public alerts, their context, the analyses run over them, and the resulting decisions in a single reproducible record.

What CTAS is

A research operations system, not an observatory pipeline

CTAS currently ingests public alert and follow-up records from survey and community services, screens every record against explicit data-rights rules before its scientific content is stored, normalizes it into a common event model, and preserves an immutable provenance envelope with checksums for everything it retains.

On top of that record it computes gated local analyses — light-curve fits, host-galaxy association, spectrum quality checks, observability windows — and presents the result through a dashboard whose job is to help a human decide what deserves attention.

The project's own internal assessment is deliberately conservative: it describes the current instance as a certification-ready research operations system, not a certified production observatory service and not an autonomous discovery or publication machine. The website follows that same line.

My role

I am designing and developing CTAS as an astronomy software project, including its scientific workflow, data model, rights-handling rules, analysis layers, and the researcher-facing interface.

What CTAS deliberately does not do.

It does not command telescopes, submit observations, publish classifications, or treat holding a credential as permission to retain data. Outbound email and webhook delivery is off by default, and every such message stays a draft until a runtime switch, an enabled policy, an exact destination and explicit per-item authorization all exist.

Workflow

How a record moves through CTAS

Each stage is marked with its real maturity. Nothing on the roadmap is drawn as though it were finished.

  • Implemented
  • Implemented, validating
  • Experimental
  • Planned

  1. Alert and follow-up intake

    Implemented

    Connectors for public transient reports, released community notes, circular streams and archival services pull records on their own schedules, with per-source status reported honestly when a service is unconfigured or unavailable.

  2. Rights screening and normalization

    Implemented

    Records must carry an accepted rights label before their scientific content enters storage, caches, responses or metrics. Anything unknown, proprietary, embargoed or restricted is refused up front, and only a minimal audit row is kept.

  3. Context and cross-matching

    Implemented

    Retained events are enriched with catalog and host-galaxy context and matched against archival services, so a candidate arrives at triage with its surroundings already attached.

  4. Candidate detection and triage

    Implemented, review-only

    A bounded local image-differencing and candidate-extraction path feeds a persistent review queue with accept, reject, needs-review and link decisions. No candidate is promoted to an operational event without a substantive human note.

  5. Classification and analysis

    Implemented, validating

    Every real event can receive a modality-aware, immutable classification assessment, including explicit conflicting-evidence and insufficient-data states. Light-curve fits, colour-temperature screening, spectrum quality checks and host ranking are produced as versioned machine evidence — not as calibrated posteriors.

  6. Science-interest and anomaly scoring

    Experimental

    Population anomaly scores and a separate science-interest score rank what looks unusual within the events CTAS has retained. Both remain experimental until their frozen expert benchmarks pass every preregistered threshold and a human adoption review happens.

  7. Notification and follow-up drafting

    Implemented, delivery gated

    Versioned notification policies, quiet hours, deduplication windows, a durable outbox and acknowledgement tracking all work. Observability planning covers altitude, airmass, twilight, Moon separation and visibility windows. Every plan is immutable, reproducible and explicitly non-submittable.

  8. Publication products and provenance

    Implemented, validating

    A target can produce a deterministic, content-addressed package of vector figures, tables, methods, captions, references and a manuscript scaffold, with checksums throughout. The certification gates that would make such a package publication-grade are explicitly not met.

  9. Certified production operation

    Planned

    A calibrated survey image feed, high-availability storage, independently witnessed disaster-recovery and load evidence, and an active on-call policy are all open gates. Until they close, CTAS stays a local research instance.

Current status

Capabilities, honestly graded

Grouped by what the code, tests and configuration actually support today.

Implemented

  • Rights-gated ingestion with fail-closed refusal of unlabelled or restricted records
  • Immutable provenance envelopes and SHA-256 content addressing
  • Durable work queue with retries and dead-letter handling
  • Local FITS image differencing and candidate extraction, review-only
  • Persistent triage queue requiring a human note before promotion
  • Host-galaxy association and catalog enrichment
  • Observability, airmass, twilight and Moon-separation planning
  • Notification policies, outbox, receipts and acknowledgement
  • Prometheus metrics, structured logs, role-scoped write authentication
  • Alembic migrations, backup and restore verification

Validating

  • Modality-aware event classification assessments
  • Multiband light-curve modelling and colour-temperature screening
  • Spectrum quality control and checksum-pinned template comparison
  • Gravitational-wave sky-map ranking and probability tiling
  • Deterministic publication-product bundles
  • Independent artifact-review workflow infrastructure

Experimental

  • Science-interest scoring, pending its frozen expert benchmark
  • Population anomaly screening within the retained event set
  • Email and HTTPS webhook delivery adapters, present but disabled by default

Planned or not certified

  • A calibrated survey image feed and survey-grade detection performance
  • Artifact modelling, completeness studies and injection/recovery evidence
  • High-availability database and replicated object storage
  • Externally witnessed disaster-recovery and sustained-load certification
  • Weather, live schedule and exposure-time integration
  • Any telescope request, control or submission path
  • SMS and mobile push delivery providers

Under the hood

Technical shape

Only components that are active in the current codebase.

Languages
Python 3.11+ for the service and analysis layers; TypeScript for the dashboard.
Service framework
FastAPI with asynchronous SQLAlchemy, Pydantic models and Uvicorn.
Dashboard
A small TypeScript application built with Vite, deliberately without a UI framework, served as static assets by the API.
Storage
PostgreSQL for the deployment topology; SQLite in WAL mode for single-machine development. Schema managed with Alembic migrations.
Scientific stack
Astropy and astropy-healpix, NumPy and SciPy.
Data formats
FITS images, fixed-NSIDE and multi-order HEALPix sky maps, Avro alert payloads, two-column ASCII spectra, and CSV/LaTeX table output. Everything retained is checksummed.
Astronomy services
Public transient-report and community-note feeds, circular streams across multiple messengers, broker output, and archival catalog and photometry services. Each source reports its own configured, unavailable or rights-blocked state rather than failing silently.
Operations
Prometheus metrics, JSON structured logging, security headers, append-only security audit rows, a durable queue with dead-letter handling, and a live readiness report.
Tests
108 test modules run under pytest with asyncio support and coverage; linting with Ruff and type checking with mypy.
Run model
Local only. A Docker Compose stack brings up the database, API, worker and migration services, bound to the loopback interface. There is no public deployment.

The status above mirrors the CTAS project itself and was last checked against the source on 18 August 2026.

Availability

Seeing more of it

CTAS is developed in a private working tree and runs only on local hardware, so there is no public repository, hosted demonstration or issue tracker to link to yet. Public documentation is in preparation.
