Cowboy Transient Alert System

CTAS

CTAS brings public supernova and multimessenger alerts together with follow-up reports and information already known about the same area of sky. It gives a researcher one place to check what was reported, what others have found, and whether the event deserves a closer look.

    What it is

    A research tool, not an automated observatory

    CTAS collects public alerts and follow-up records. Before it stores any scientific content, it checks the record against a set of data-rights rules. Accepted records are converted to a common format, and CTAS keeps the original source information and a checksum for each one. It can then run local analyses such as light-curve fits, host-galaxy matching, spectrum checks and observability calculations. A researcher reviews the results.

    CTAS is still research software under active development. It is being built toward eventual production use, but it is not a certified service and it does not make or publish discovery claims on its own. I design and develop its scientific workflow, data model, data-rights rules, analysis tools and interface.

    What CTAS does not do.

    It does not control telescopes, submit observing requests, or publish classifications. Access to a source does not automatically mean its data can be stored. Email and webhook delivery are disabled by default, and each message remains a draft unless delivery is enabled, the policy allows it, the destination is specified and that item has been approved.

    Workflow

    How a record moves through CTAS

    Each stage shows its current status. Planned work is not presented as finished.

    • Implemented
    • Implemented, validating
    • Experimental
    • Planned

    1. Intake

      Implemented

      Connectors collect public transient reports, released community notes, circulars and archival records. Each connector also reports whether it is configured, unavailable or blocked by data-rights restrictions.

    2. Rights screening and normalization

      Implemented

      CTAS stores scientific content only after a record receives an accepted rights label. Records marked unknown, proprietary, embargoed or restricted are rejected before they can enter storage, caches, responses or metrics.

    3. Context and triage

      Implemented, review-only

      CTAS adds catalog and host-galaxy information, then places each event in a review queue that remains available between runs. A researcher must leave a meaningful review note before the event can move into follow-up planning.

    4. Classification and analysis

      Validating

      CTAS records a separate assessment for each kind of evidence and keeps every version. It can state when the evidence conflicts or when there is not enough data. Light-curve and spectrum results are stored as machine-generated evidence, not treated as calibrated probability estimates.

    5. Follow-up drafting and public export

      Implemented, delivery gated

      CTAS calculates observability, applies saved notification rules, prepares messages in an outbox and creates the sanitized public export used on this page. Follow-up plans are saved with the information needed to reproduce them. CTAS cannot submit those plans to an observatory.

    6. Certified production operation

      Planned

      Before CTAS could run as a certified production service, it would still need a calibrated survey image feed, high-availability storage, independently reviewed disaster-recovery and load tests, and a formal on-call policy.

    Under the hood

    How it is built

    Languages
    Python 3.11+ for the service and scientific analysis; TypeScript for the operations dashboard.
    Service
    FastAPI with asynchronous SQLAlchemy, Pydantic models, a durable work queue and Alembic migrations.
    Storage
    PostgreSQL for deployed systems; SQLite in WAL mode for development on one machine.
    Scientific stack
    Astropy and astropy-healpix, NumPy and SciPy. CTAS reads FITS images, HEALPix sky maps, Avro alerts and two-column ASCII spectra, and records a checksum for every retained file.
    Tests
    The test suite contains 108 pytest modules, with coverage reporting, Ruff linting and mypy type checking.
    Public refresh
    A scheduled GitHub Actions job runs CTAS, creates the sanitized dataset shown above and republishes this site. Credentials and internal records are not included in the public files.
