Cowboy Transient Alert System

CTAS

A rights-aware system that reconciles supernova and multimessenger alerts with public follow-up evidence, so a researcher can see in one place what was reported, what is already known about that patch of sky, and what is worth doing next.

    What it is

    A research operations system, not an observatory pipeline

    CTAS ingests public alert and follow-up records, screens every record against explicit data-rights rules before its content is stored, normalizes it into a common event model, and keeps an immutable provenance envelope with checksums for everything it retains. On top of that it runs gated local analyses — light-curve fits, host association, spectrum checks, observability windows — and surfaces the result for a human to judge.

    Its own internal assessment is deliberately conservative: a certification-ready research operations system, not a certified production service and not an autonomous discovery machine. I design and develop it — the scientific workflow, data model, rights rules, analysis layers and interface.

    What CTAS deliberately does not do.

    It does not command telescopes, submit observations, publish classifications, or treat holding a credential as permission to retain data. Outbound email and webhook delivery is off by default; every such message stays a draft until a runtime switch, an enabled policy, an exact destination and per-item authorization all exist.

    Workflow

    How a record moves through CTAS

    Each stage carries its real maturity. Nothing on the roadmap is drawn as finished.

    • Implemented
    • Implemented, validating
    • Experimental
    • Planned

    1. Intake

      Implemented

      Connectors pull public transient reports, released community notes, circular streams and archival records, each reporting its own configured, unavailable or rights-blocked state.

    2. Rights screening and normalization

      Implemented

      A record must carry an accepted rights label before its scientific content enters storage, caches, responses or metrics. Unknown, proprietary, embargoed or restricted records are refused up front.

    3. Context and triage

      Implemented, review-only

      Events are enriched with catalog and host-galaxy context and enter a persistent review queue. Nothing is promoted to an operational event without a substantive human note.

    4. Classification and analysis

      Validating

      Modality-aware immutable assessments, including explicit conflicting-evidence and insufficient-data states, plus light-curve and spectrum analysis as versioned machine evidence — not calibrated posteriors.

    5. Follow-up drafting and public export

      Implemented, delivery gated

      Observability planning, durable notification policies and an outbox, plus the sanitized public export that feeds this page. Plans are immutable, reproducible and explicitly non-submittable.

    6. Certified production operation

      Planned

      A calibrated survey image feed, high-availability storage, externally witnessed disaster-recovery and load evidence, and an on-call policy all remain open gates.

    Under the hood

    Technical shape

    Languages
    Python 3.11+ for the service and analysis layers; TypeScript for the operations dashboard.
    Service
    FastAPI with asynchronous SQLAlchemy, Pydantic models, a durable work queue and Alembic migrations.
    Storage
    PostgreSQL for the deployment topology; SQLite in WAL mode for single-machine development.
    Scientific stack
    Astropy and astropy-healpix, NumPy and SciPy. FITS images, HEALPix sky maps, Avro alerts and two-column ASCII spectra, all checksummed.
    Tests
    108 test modules under pytest with coverage, Ruff and mypy.
    Public refresh
    A scheduled GitHub Actions job runs CTAS, exports the sanitized dataset above, and republishes this site. No credentials or internal records reach the browser.

    Project status above mirrors the CTAS source and was last checked on 18 August 2026.
